UC-001

Register and sign in

Must

A person creates a Tezera account with one role, verifies their email address or phone number, and signs in on the app (planned, not built) or the web portal. Email accounts use a password and a six-digit email code. Phone accounts have no password: Cognito texts a code at every sign-in.

Priority
Must
Primary actor
Registered user (consumer, organiser, vendor or freelancer)
Supporting actors
Amazon Cognito (sends the codes with its built-in email and SMS; this replaces the earlier plan for Dialog e-SMS and Amazon SES, which are planned, not built); the pre-sign-up and post-confirmation Lambda triggers
Before it starts
The person has no account for this email address or phone number. The device is online.
Trigger
The person taps "Sign up".

Main flow

ActorSystem
  1. Actor1. Enters an email address or phone number, a password (email accounts only) and a date of birth, and picks one role.
    System2. Checks the person is 16 or over (proposed); the pre-sign-up trigger also allows only the roles consumer (`attendee` in the code), organiser, vendor and freelancer, and blocks admin. For under-18s, asks them to confirm a parent or guardian agreed.
  2. Actor3. Ticks the guardian box, if asked, and submits.
    System4. Creates the account in Amazon Cognito, adds it to the group for that role (post-confirmation trigger), and sends a one-time code.
  3. Actor5. Enters the code.
    System6. Confirms the account, signs the person in, and moves them on by the `custom:setup` attribute: profile setup, then verification (organiser, vendor and freelancer only), then the home screen for their role. The user record is created on the first guarded API call (`GET /me`); the web portal does not call the API yet, so profile details and uploaded files are not saved yet.

Exception flow

ActorSystem
  1. ActorE1. Enters a date of birth under 16.
    SystemRefuses the sign-up and says the minimum age is 16.
  2. ActorE2. Enters a wrong or expired code.
    SystemShows an error and offers to send a new code.
  3. ActorE3. Uses an email address or phone number that already has an account.
    SystemSays an account exists and offers "Sign in" and "Forgot password".

Alternate flow

ActorSystem
  1. ActorA1. An existing user enters their email address and password (and the emailed code), or their phone number and the code texted to them.
    SystemChecks them with Cognito and opens the home screen for the user's role.
  2. ActorA2. Taps "Forgot password" and enters the code sent to them and a new password.
    SystemResets the password and shows a "Password changed" screen with a link to log in. It does not sign the user in. Phone accounts have no password to reset.
Out of scope
Sign-in with Google or Apple (not in the PRD; a Google button and a commented-out Cognito Google provider exist in the code as a stub, not working). Choosing more than one role at sign-up; the code does not stop an account being put in several Cognito groups later, and the highest-priority group (admin, organiser, vendor, freelancer, consumer) becomes `users.role`.
After it ends
A verified account exists in a role group, with a matching user record in the database once the first guarded API call is made. The account status is `pending`, `active`, `suspended` or `banned`; the API rejects any status other than `active` with `ACCOUNT_NOT_ACTIVE`. Other 403 codes: `ROLE_MISSING`, `CONTACT_NOT_VERIFIED`, `PROFILE_FAILED`, `ROLE_NOT_ALLOWED`. A missing or invalid token gives 401.
PRD rowsAC-01
Functional requirementsFR1, FR2
  • FR1 The system shall let a user sign up with an email address or phone number, verify it with a one-time code, and pick one role: organiser, vendor, freelancer or consumer.
  • FR2 The system shall refuse sign-up to anyone under 16 (proposed) and ask under-18s to confirm a parent or guardian agreed.

UC-002

Get verified

Must

An organiser or provider uploads verification documents; an admin checks them and approves or rejects the account.

Priority
Must
Primary actor
Organiser or provider
Supporting actors
Admin; notification services
Before it starts
The user is signed in as an organiser, vendor or freelancer and is not yet verified.
Trigger
The user opens "Get verified", or tries an action that needs verification (UC-007, UC-008, UC-010).

Main flow

ActorSystem
  1. Actor1. Uploads the documents asked for (proposed: business registration for companies, NIC for individuals).
    System2. Stores them in a private location only admins can read, and adds the request to the admin queue.
  2. Actor3. Admin opens the request and views the documents.
    System4. Shows each document through a short-lived signed link.
  3. Actor5. Admin approves.
    System6. Marks the account verified, shows the Verified badge, unlocks hiring, stalls and bookings, logs the decision and notifies the user.

Exception flow

ActorSystem
  1. ActorE1. Uploads a file that is too large or of the wrong type.
    SystemRejects the file and says why.
  2. ActorE2. Admin rejects the request and gives a reason.
    SystemNotifies the user with the reason; the user can upload new documents.

Alternate flow

ActorSystem
  1. ActorA1. An unverified organiser tries to post a job.
    SystemBlocks the action and opens "Get verified".
Out of scope
Automatic checks against government records. Verification of consumers.
After it ends
The account is verified or rejected, with the admin's name, time and reason in the audit log.
PRD rowsAC-08 AC-09 AD-01
User storiesUS-C05 US-P04 US-A01
Use casesRefers to UC-007 UC-008 UC-010
Functional requirementsFR7, FR8
  • FR7 The system shall let organisers and providers upload verification documents, and let admins approve or reject them with a reason.
  • FR8 The system shall stop unverified organisers from opening stalls, posting jobs or sending booking requests, and unverified providers from accepting bookings.

UC-003

Publish and manage an event

Must

An organiser creates an event page, publishes it, and keeps it up to date, including its live status on the day.

Priority
Must (live status, "Know before you go" and age rating: Should)
Primary actor
Organiser
Supporting actors
Consumer (receives updates); notification services
Before it starts
The organiser is signed in.
Trigger
The organiser taps "New event".

Main flow

ActorSystem
  1. Actor1. Enters title, category, date and time, venue, description, cover image, line-up, entry price or "free", age rating, and optional "Know before you go" fields and a ticket link.
    System2. Validates the required fields and saves a draft.
  2. Actor3. Taps "Publish".
    System4. Publishes the page, creates its discussion board and Q&A, and makes it searchable.
  3. Actor5. Later changes the date, time or venue.
    System6. Saves the change and notifies everyone who marked the event 'Going' or 'Interested'.

Exception flow

ActorSystem
  1. ActorE1. Leaves a required field empty or sets a date in the past.
    SystemKeeps the draft and highlights the field.
  2. ActorE2. Cancels the event.
    SystemAsks for confirmation, marks it cancelled, closes its stall applications and job posts, and notifies 'Going' and 'Interested' consumers by push, and urgently by SMS.

Alternate flow

ActorSystem
  1. ActorA1. On the day, sets the status to "Running late" with a new start time.
    SystemShows the status on the event page and pushes it to 'Going' and 'Interested' consumers.
Out of scope
Selling tickets and QR entry (after the ATP). Checking attendees' ages (organisers check ID at the gate).
After it ends
The event is published (or saved as a draft) and every change is visible to consumers.
PRD rowsEV-01 EV-02 EV-08 EV-09 EV-10
User storiesUS-C03 US-C04 US-C06 US-C07 US-C13 US-C20 US-O12
Use casesReferred to by UC-006
Functional requirementsFR10, FR11, FR15, FR17, FR18, FR19
  • FR10 The system shall let organisers create, save as a draft, publish, edit, postpone and cancel an event page with title, category, date and time, venue, description, cover image, line-up and entry price.
  • FR11 The system shall notify consumers who marked an event 'Going' or 'Interested' when its date, time or venue changes, or when it is postponed or cancelled.
  • FR15 The system shall let consumers search events by keyword, category, date, district, price, free entry and age rating.
  • FR17 The system shall show a "Know before you go" section (dress code, parking and transport, what to bring, rules, food and drink prices, rain cover) and hide empty fields.
  • FR18 The system shall let organisers set an event's live status (on time, running late with a new start time, postponed, cancelled) and push it to 'Going' and 'Interested' consumers.
  • FR19 The system shall show each event's age rating: All ages, 18+ or 21+.

UC-007

Send a direct booking request

Must

An organiser finds a provider and sends a booking request with a brief, budget and terms; the provider accepts, declines or quotes.

Priority
Must
Primary actor
Organiser
Supporting actors
Provider (vendor or freelancer); notification services
Before it starts
The organiser is verified and has a published or draft event. The provider is verified.
Trigger
The organiser taps "Request booking" on a provider's profile.

Main flow

ActorSystem
  1. Actor1. Searches providers by category, district, rating, rank, verified status and available date, and opens a profile.
    System2. Shows results ordered by rank score, and the profile with portfolio and reviews.
  2. Actor3. Picks the event, date, times and budget; fills any of the brief fields (service, duration, audience, deliverables, run-of-show, equipment); sets payment and cancellation terms.
    System4. Sends the request to the provider and notifies them.
  3. Actor5. Provider reads the brief and terms and taps "Accept".
    System6. Runs UC-019: creates the confirmed booking with the agreed service, date, price and terms, and notifies the organiser.
  4. Actor7. After the event, the organiser marks the booking completed.
    System8. Opens reviews for both sides (UC-013).

Exception flow

ActorSystem
  1. ActorE1. Provider declines.
    SystemNotifies the organiser and suggests other providers from the same search.
  2. ActorE2. Either side cancels a confirmed booking within 7 days of the event (proposed).
    SystemRecords the late cancellation on the canceller's profile. If the provider cancelled, offers the organiser a job post prefilled from the booking.

Alternate flow

ActorSystem
  1. ActorA1. Provider replies with a different quote and terms.
    SystemSends the quote to the organiser; the booking is created only if the organiser accepts it.
Out of scope
Hiring for private events with no public event page (open question). Contracts with legal force.
After it ends
A confirmed booking exists with its brief, price and terms on record, or the request is closed as declined.

UC-009

Make a test payment

Should

An organiser pays a deposit or instalment on a booking, or a vendor pays a stall fee, through the payee's own PayHere merchant account in sandbox mode. No real money moves.

Priority
Should
Primary actor
Organiser (instalments) or vendor (stall fees)
Supporting actors
PayHere sandbox; the payee (provider or organiser)
Before it starts
A confirmed booking with payment terms, or an approved stall with a fee. The payee has connected a PayHere sandbox merchant account.
Trigger
The payer taps "Pay" on an instalment or stall fee.

Main flow

ActorSystem
  1. Actor1. Taps "Pay" and confirms the amount.
    System2. Records a pending payment and opens the payee's PayHere checkout (hosted page on the web, PayHere SDK in the app), labelled "Test payment, no real money".
  2. Actor3. Pays with a PayHere test card.
    System4. PayHere calls Tezera's notify route. The system checks the signature, updates the payment once per order ID, and marks the instalment received or the stall paid.
  3. Actor—
    System5. Sends both sides a receipt that shows Tezera's commission as a separate line, not charged.

Exception flow

ActorSystem
  1. ActorE1. The payment fails or is cancelled at checkout.
    SystemKeeps the instalment due and tells the payer.
  2. ActorE2. A notice arrives with a bad signature, or a second time.
    SystemIgnores it and logs it; the payment does not change.

Alternate flow

ActorSystem
  1. ActorA1. The payee has no connected account.
    SystemHides "Pay"; the payer pays outside the app and the payee marks the instalment received (payment tracking, HR-15).
Out of scope
Real money. Tezera collecting, holding or splitting funds. Ticket payments and refunds.
After it ends
The payment record, instalment or stall status, and both receipts are stored and visible to admins in disputes.

Build the venue map

Must

An organiser builds the event's venue map in the web map builder: zones, stalls and pins over a floor plan or grid, to scale, then publishes it.

Priority
Must (PDF, blank grid and saved venue maps: Should; AI first draft: Could)
Primary actor
Organiser
Supporting actors
Amazon Bedrock (AI first draft, Could)
Before it starts
The organiser is signed in on the web portal and the event exists.
Trigger
The organiser opens "Venue map" on the event.

Main flow

ActorSystem
  1. Actor1. Uploads a floor plan image (PNG or JPG).
    System2. Sets it as the background layer.
